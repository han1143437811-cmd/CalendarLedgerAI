# Fossify 日历账本 AI：功能与开发规格

记录日期：2026-10-04。目标设备：Samsung S24 Ultra，无 Root，用户报告系统为 One UI 8.5。

状态：已完成官方资料与部分源码的可行性核查，本文是拟开发规格。尚未克隆或修改 Fossify 源码，尚未构建 APK、调用用户 API 或在目标手机上测试。以下“需要支持”均是开发要求，不代表原版软件已经提供这些功能。

## 1. 已确定的目标

基于 Fossify Calendar 源码制作可直接安装的 Android 应用，接入用户自行配置的 DeepSeek API。AI 是整个应用的操作入口，需要覆盖日程、待办、提醒、账本、分析、视图、设置、日历管理、导入导出与备份；手动界面与 AI 使用同一套业务逻辑。

“全部功能”的验收含义：当前定制版本中每个用户可见功能都有能力登记、对应操作入口、结果反馈和验证案例。应用内可直接处理的功能由 AI 调用；Android 授权、账号登录、文件位置选择、系统分享和打印等操作由 AI 打开相应界面，完成后读取应用能够获得的结果。不能将打开系统页面描述为已成功完成授权、同步、分享或打印。

开发可以分阶段交付，但最终目标覆盖整个应用，不能用“只有聊天和新增记账”作为完成标准。

## 3. 全应用功能覆盖

| 日程制定 | 查询已知日程，按时长、时间范围、工作时间和缓冲要求找空档；调整已选日程 | “下周工作日下午给我安排三次各两小时的论文写作。” | 新增空档计算、冲突检查与方案生成；查询范围要显示。 |
| 待办 | 新建、修改、删除、查询、完成/恢复未完成；截止时间、提醒和重复规则 | “周五前整理报销材料，完成后把它划掉。” | 接入现有待办服务；跨设备待办同步另需实现和验证。 |
| 提醒与通知 | 添加/删除/调整提醒；默认提前时间、应用内延后规则；查询提醒状态 | “以后新日程都提前 15 分钟提醒。” | 与通知及闹钟调度共用逻辑；系统控制项打开对应设置页。 |
| 日历管理和同步 | 管理本地日历、颜色、默认日历和显示筛选；选择已授权的系统日历并触发刷新 | “工作日程默认写到工作日历，只显示工作和个人两个日历。” | 封装日历服务；检查目标日历是否可写，并区分本地保存与远端同步。 |
| 视图与导航 | 日、周、月、月加日、年和列表视图；日期跳转、检索、筛选 | “打开上个月，只看餐饮账目和出差日程。” | AI 可以改变实际界面，返回可打开的日期或结果。 |
| 日历记账展示 | 月格显示每日收入、支出及净额；选择日期查看账目和日程；切换显示内容 | “这个月每天分别花了多少？打开花费最高的那一天。” | 新增账本与日历的联合展示和跳转。 |
| 节假日、生日和纪念日 | 管理现有导入入口、显示和提醒规则；对需要读取联系人的行为请求对应权限 | “把生日提醒设为提前一天。” | 核查具体功能和权限后逐项接入；不假定已读取联系人。 |
| 外观与小组件 | 主题、字体、周起始日、24 小时制、默认视图、显示项、小组件颜色及刷新 | “改成周一开始、24 小时制，字体调大一点。” | 可由应用设置的项直接改；桌面添加和系统配置由相应界面完成。 |
| 导入、导出、分享和打印 | 日程 ICS；账本 CSV/JSON；筛选导出；打开分享、打印界面；查询导出文件结果 | “导出今年旅行支出和下周日程。” | 复用日程迁移能力，补做账本格式和系统界面衔接。 |
| 备份与恢复 | 手动备份、自动备份规则、预览恢复范围和执行恢复 | “每周备份一次，把本月账目也备份进去。” | 新备份需要覆盖账本、日程关联、预算及配置；不把 API Key 默认放进明文备份。 |
| AI 与应用设置 | 查看可用功能、配置提供商地址和模型、测试连接、管理会话、打开帮助/关于页面 | “以后普通操作用快速模型，打开 API 设置。” | 新增 AI 配置及能力查询；密钥通过专门输入框设置，不在聊天里回显。 |

参与人、日程状态、可见性等依赖日历提供者的字段，应根据固定版本中的实际支持情况登记；AI 只能提交应用与目标日历允许的字段。对只读日历应反馈原因，并在用户选择后复制到可写日历。

## 4. 操作接口与执行流程

推荐结构：AI 对话界面 → DeepSeek 工具调用 → 本地操作调度器 → 日程/待办/账本/设置服务 → 数据库或系统日历提供者 → 执行结果卡片。

手动按钮同样调用这些服务。不能让 AI 通过任意 SQL、生成代码或模拟点屏幕来完成普通应用内业务操作。

下面是拟定的接口分组，实际参数表在固定源码版本后制定。每个修改接口应有明确字段和枚举，不接受任意内部配置名称。

| 接口分组 | 拟定工具 | 主要约束 |
| --- | --- | --- |
| 能力及上下文 | `list_capabilities`、`get_app_context`、`get_operation_status` | 返回版本、当前日期/时区、页面日期、授权状态和实际可用能力。 |
| 账目 | `search_transactions`、`get_transaction`、`create_transactions`、`update_transaction`、`delete_transactions` | 金额、币种和收支类型分开；修改必须指向确定记录。 |
| 账本、账户和分类 | `manage_ledger`、`manage_account`、`manage_category`、`record_transfer`、`record_refund` | 每个管理操作列举允许动作；合并或删除显示受影响记录。 |
| 预算与周期项目 | `manage_budget`、`query_budget`、`manage_recurring_bill` | 区分预计发生与已实际记录的收支。 |
| 统计 | `query_cashflow`、`compare_cashflow`、`get_supporting_transactions`、`open_report` | 可审计的统计口径；结果带数据版本及来源记录范围。 |
| 日程 | `search_events`、`get_event`、`create_event`、`update_event`、`delete_events`、`duplicate_event` | 修改重复项目时显式指定 occurrence / future / series。 |
| 制定日程 | `find_free_slots`、`plan_schedule`、`apply_schedule_plan` | 已知日程范围、时长、缓冲和固定日程规则；保存前复查冲突。 |
| 待办 | `search_tasks`、`create_task`、`update_task`、`delete_tasks`、`set_task_completion` | 重复待办须明确对应发生日期和修改范围。 |
| 提醒 | `manage_reminders`、`get_reminder_status` | 业务对象提醒与系统通知权限状态分开返回。 |
| 日历与同步 | `list_calendars`、`manage_calendar`、`set_calendar_visibility`、`refresh_calendar_sync` | 返回本地/系统来源、可写性、刷新结果及远端状态是否可确认。 |
| 导航与配置 | `navigate_calendar`、`open_record`、`get_settings`、`update_settings`、`manage_special_dates` | 仅接受登记的视图、设置字段和支持的值。 |
| 文件与备份 | `preview_import`、`apply_import`、`export_data`、`create_backup`、`manage_backup_schedule`、`preview_restore`、`apply_restore` | 文件授权范围、格式检查、导入重复处理、恢复影响预览。 |
| 系统界面与回退 | `open_system_action`、`preview_bulk_operation`、`undo_operation` | 明确打开界面与完成操作的差别；返回实际可恢复范围。 |

调度器需要完成以下过程：

1. 从手机时间与时区解析“今天、昨天、下周”；不能用模型训练日期推定当前日期。
2. 获取必要数据。修改现有对象前先检索并解析稳定 ID；“上一笔”绑定上一条操作结果。“昨天那笔咖啡”对应多个结果时再询问。
3. 检查参数、权限、目标可写性、金额范围、时间顺序及对象版本；不支持的操作返回真实原因。
4. 对明确的普通新增、单条修改和视图设置直接执行，返回结果及可用撤销入口；批量清空、覆盖恢复等操作先展示具体范围，再执行用户确认的方案。
5. 保存后读取实际结果，刷新日历、列表、小组件和提醒。结果必须包含对象 ID、关键字段、成功/部分成功/失败状态。
6. 将工具实际结果反馈给模型生成回答。无成功结果时不能显示“已记账”或“已创建提醒”。

一次请求可以包含多步操作：独立只读查询可并行，依赖前一步结果的修改按顺序执行。给每个请求和每步写入分配幂等标识；网络重试不应重复入账。手机本地事务可以保证其范围内一致性，系统日历或远端同步不能假定与本地数据库共同构成原子事务。部分失败应保留清晰状态和补救入口。

“撤销”通过操作日志与修改前版本实现；已发生外部共享、远端变化或不可恢复操作不能承诺一键完全回退。

## 5. 收支数据和分析口径

账本应使用独立结构化数据表，并通过 ID 与日程关联。日历上显示的文字只是展示，不能把日程标题中的金额当作唯一账本数据源。

最小数据结构包括：账本、账户、分类、交易、转账/退款关联、预算、周期账单、日程关联和操作日志。交易包含 ID、类型、整数最小货币单位金额、币种、发生时间与本地记账日期、分类、账户、备注/标签、关联对象、创建/更新时间、数据版本和删除状态。自动推定的分类在结果卡片中显示，并允许立即改正。

统计口径要求：

- 实际收入、实际支出、账户间转账和预计账单分别记录。内部转账不重复计算为整体收入与支出；退款、报销和信用卡还款的归类规则可配置，并在报告中显示。
- 消费分析与账户现金流需要分别定义；已记消费后再次还款不能在消费分析中重复计数。
- 账户余额需要期初余额和完整账户流水；只记录了部分消费时只能给出已记录的净收支，不能伪称真实余额。
- 同一结果明确起止日期、时区、账本、账户、分类、排除项、退款处理和币种。多币种不得直接相加；折算需要明确汇率、日期及来源。
- 本月截至今日和上月同期应按一致的时段比较；整月比较可由用户指定，并标明本月数据未完整。
- 总额、占比、排序、趋势和差额由本地程序计算，AI 使用这些结果解释。模型不可自行编造缺失金额或消费动机。
- 每个图表或结论都可以打开相关账目。大额账目是需要核查的记录，不自行定性为错误或异常消费。
- “为什么花得多”先给出可验证的分类、次数、单笔金额及具体记录变化；缺乏备注或原因信息时，应说明账目能够支持的解释范围。

支持的分析请求应包括：任意时段汇总、按分类/账户/标签比较、指定排除条件、预算使用、同周期对比、固定支出占比、指定金额范围的账目定位、日历热度和点击日期查看明细。

## 6. 实际交互要求

示例一：

> 用户：今天午饭 35、地铁 6，明天下午 2 点安排一个小时项目讨论，提前 30 分钟提醒。

应用创建两条账目和一个日程，显示日期、金额、分类、所属账户、日程起止时间及提醒是否成功设置。账户使用已设置的默认值；没有必要默认值时询问缺失项。分类可以依据明确规则推定并在卡片上提供修改入口。

> 用户：午饭改成 38，会议改到 3 点，地铁那笔撤销。

应用依据上一轮结果 ID 定位对象，修改账目和日程并移除对应地铁记录；每一步展示真实执行状态。会议若属于重复系列，应处理用户指定的范围，范围不清时先询问。

示例二：

> 用户：分析本月餐饮支出，比上月同期多在哪，排除旅行账本里的记录。

应用按手机当前日期确定本月和上月同期，查询对应记录，计算总额、次数、均价、分类变化与差额，再输出带可点击明细的解释。该示例不预置任何模拟金额作为真实结论。

> 用户：把餐饮预算设成 800，接近上限时提醒我。

应用保存预算；“接近”的阈值需要用户给定或使用明确显示的已有默认值。预算提醒属于新开发能力，需要验证通知权限、后台调度和不重复提醒。

示例三：

> 用户：下周找三个工作日下午各安排两小时论文写作，避开已有会议，前后留半小时。

应用查询已授权且纳入排程的日历，列出实际空档并形成方案。允许用户直接指定方案执行；保存时复查冲突，并明确未接入的其他日历不在本次冲突检查范围内。

界面要求：全局 AI 入口；支持在对话中连续修改；操作结果卡片可打开对象、编辑或撤销；分析卡片包含时间范围、筛选条件、图表和明细入口。手动账本、日程和待办页面在无网络时可用。

## 7. DeepSeek 接入和手机安装

应用配置包含提供商、Base URL、API Key、操作模型、分析模型和连接测试。支持官方 DeepSeek，也允许用户配置提供兼容接口的服务；第三方服务的模型名称和工具能力需要连接测试，不能假定与官方完全相同。

核查时官方文档示例使用 `https://api.deepseek.com` 和 `deepseek-flash`，API 文档列出 `deepseek-v4-pro`。具体模型名称应可配置，并在实现时再次核查。普通操作优先使用成本与延迟合适的模式，复杂分析可以选另一模型或思考模式。

如果使用思考模式工具调用，按 [DeepSeek 思考模式文档](https://api-docs.deepseek.com/guides/thinking_mode/)处理返回消息与后续请求，不在用户界面暴露内部推理。使用流式输出时，完整收集并校验参数后才执行动作，不能在参数尚未完成时写入。

API Key 在专用设置页输入，以 Android Keystore 保护的密钥加密保存。Key 不进入普通日志、对话历史或默认导出。参考：[Android Keystore 官方文档](https://developer.android.com/privacy-and-security/keystore)。

聊天内容和此次操作所需的选定记录/汇总会发送到配置的服务；账本和日程本地存储。每次分析先做本地筛选和汇总，仅在解释或细节核查需要时发送对应明细。新增联网行为应在定制版的设置和隐私说明中准确描述。

采用独立包名、应用标识和签名生成 APK，允许与原版共存。实现路线无需 Root 或 LSPatch。安装后由用户通过正常 Android 界面授予所需日历、通知及适用的提醒调度权限；用户报告的系统版本和后台行为需要在真实 S24U 上验证。

云端会话不可用、API 超时或余额不足时，应用应明确报错并允许重试；手动业务与本地统计继续可用。网络错误后的重试先查询操作状态，避免重复写入。

## 8. 开发阶段与交付要求

| 阶段 | 实际产物 | 完成条件 |
| --- | --- | --- |
| A：固定基线与完整盘点 | 固定 Fossify 提交、构建配置、全功能覆盖矩阵 | 每个菜单、编辑字段、设置、通知动作和小组件入口有编号及处理方式。 |
| B：共享服务与账本 | 可运行的日程/待办服务，结构化账本、日历联合展示和本地统计 | 手动操作可用，提醒/重复规则无回归，账目与日历视图一致。 |
| C：全应用 AI 接口 | 能力登记、工具参数、连续会话、操作结果卡片和日志 | 全部已实现业务功能可通过 AI 调用；系统动作正确衔接。 |
| D：制定日程与分析 | 空档排程、冲突处理、统计报告、图表和记录追溯 | 在真实数据上遵守时间约束，统计可核对，结论能定位明细。 |
| E：备份与真机验收 | 完整备份格式、可安装 APK、源码及构建说明 | S24U 无 Root 安装、授权、后台提醒、失败恢复和完整覆盖验证通过。 |

以上顺序是实现依赖，整体完成需要 A—E。阶段 B 或 C 的局部演示不能代替最终验收。

## 9. 必须通过的验收情形

| 编号 | 情形 | 验收要求 |
| --- | --- | --- |
| T01 | 一次多笔记账并创建带提醒日程 | 对象数量、金额、日期及提醒与要求一致，返回可打开的真实对象。 |
| T02 | 连续对话修改金额、时间并撤销其中一笔 | 按上一轮稳定 ID 操作，没有改到同名的其他记录。 |
| T03 | 模糊对象、缺少时间或重复系列范围 | 获取缺失信息后再写入，其他已明确的独立查询可以继续。 |
| T04 | 重复日程/待办的本次、此后和整个系列修改 | 各范围按预期改变；其他发生实例不被误改，提醒正确刷新。 |
| T05 | 根据现有日程找空档并安排多个事项 | 对已接入日历进行冲突检查，满足时长、工作时间和缓冲要求。 |
| T06 | 退款、内部转账、还款和未完成周期账单参与统计 | 遵守显示的口径，消费统计不重复计数，未付款预计项不混入实际支出。 |
| T07 | 用户自定义分析及上月同期对比 | 日期、排除条件和分组准确，结果与人工核对一致，可定位贡献记录。 |
| T08 | AI 改视图、筛选、默认提醒、主题或显示设置 | 实际界面和配置发生对应变化，小组件及相关页面及时更新。 |
| T09 | 批量修改/删除、备份、导入及恢复 | 显示具体影响范围；重复导入有规则；恢复后账本、关联和设置一致。 |
| T10 | 只读日历、拒绝授权或同步不可确认 | 返回真实限制与可行操作，不报告没有完成的保存、提醒或远端同步。 |
| T11 | API 中断、错误参数、重复发送和进程重启 | 不重复入账；已完成与未完成步骤可区分，并能查询和恢复操作状态。 |
| T12 | S24U 熄屏、重启、后台限制下的提醒与周期任务 | 在实机条件下记录触发结果和需要的系统设置；不以模拟器结果代替真机验收。 |
| T13 | 全功能清单与 AI 能力对照 | 所有应用内功能都有已验证接口或明确系统衔接；未完成项不计为已支持。 |

待后续开发时确认、无需阻塞本规格的事项：最终应用名称及图标、默认账本/账户、预算提醒阈值、是否需要语音输入或票据图片导入、实际使用的 API 提供商与模型。API Key 只需在未来应用的专用配置界面输入。
